# 架构说明模板

这份模板由学习者在实现过程中逐步填写。目前不是“完整项目已实现”的声明。

## 问题与输入输出

输入仓库：______。问题描述：______。
允许修改：______。任务最终成功由哪份外部测试判定：______。
输出补丁、轨迹、测试结果与状态分别保存在哪里：______。

~~~mermaid
flowchart LR
  U[任务与受限工作区] --> L[Agent 循环]
  L --> M[宿主侧模型客户端]
  M --> L
  L --> T[校验与工具执行器]
  T --> W[隔离工作区与测试容器]
  T --> L
  L --> S[状态存储与事件轨迹]
  S --> L
  W --> G[工作区外的独立评分]
~~~

图为目标结构。实现后逐项标明“已实现 / 简化模拟 / 未实现”，特别区分 Docker 与普通子进程。

## 接口与不变量

为消息、tool_call_id、工具请求、结构化错误、任务状态列一个最小实例。
列出预算在何处检查、何时计数、哪些分支会消耗次数。
说明未知工具、参数错误、权限拒绝、文件越界、超时的处理顺序。

## 状态与恢复

保存哪些字段，为什么足够继续；schema_version 怎样升级；
工作区指纹覆盖哪些文件；检查点在哪个边界提交。
列出执行前、执行后提交前、提交后崩溃时的行为。
说明无法保证 exactly-once 的窗口，以及对只读工具、写工具和计费调用采用何种补救。

## 上下文与记忆

完整轨迹和模型视图怎样分开；长输出怎样处理；
摘要怎样回查证据；长期事实怎样保存与更新；旧事实怎样被发现。
如果没有长期记忆就明确写未实现，不把恢复数据库称为完整记忆系统。

## 安全与运行假设

主机密钥如何避免传入容器；容器挂载、网络、权限、时间和资源限制是什么；
评分测试是否只读且不可被工具写入；路径和符号链接边界怎样验证。
列出现实假设与未覆盖风险，不能只写“有 Docker 所以安全”。

## 设计选择与验证

每个决定用“问题→选择→代价→证据”解释。
至少包括 SQLite、消息协议、工具集合、上下文策略和外部评分。
附测试命令、真实运行配置、失败样例与实验报告，不复制别人的项目成绩。
