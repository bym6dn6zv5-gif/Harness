# 第 11 周：冻结实现，运行最终评测

[回学习时间表](../../docs/study-calendar.md#w11) · [上一周](week10.md) · [下一周](week12.md)

本周主教材任务：固定提交、配置与复现。按 [源码任务表](../source_mastery/curriculum-map.md) 对照 claw-code 与 Codex，
先读 [主讲义](../source_mastery/README.md)，再提交本周 Python 实现与一个失败反例。

周成果：基线与改进版的结果表、原始记录、成本账本、失败分析和复现说明。
只有前面实验成立并且预算可承受时，才开启保留集。额度不足就保留未运行状态。

<a id="w11-d01"></a>

## 第 1 天：冻结实验方案

记录基线 commit、改进版 commit、任务材料指纹、模型标识、采样参数、工具策略、预算、镜像 id。
提前写好评分规则、重复次数和中断计入方式，冻结后不根据保留集表现调策略。
小例子：两个版本 × 10 保留任务 × 3 次独立重复，共计划 60 次任务运行。
这不是 60 次 API 请求，每个任务可能包含多次调用与重试。
验收：冻结清单已经提交，预计上界没有突破剩余 100 元总预算。
基础：可复现配置与可变外部服务。

<a id="w11-d02"></a>

## 第 2 天：离线演练

用回放模型先演练目录分配、任务复制、评分、日志和汇总；检测漏行与覆盖。
再选择开发任务做极小真实预检，核对连接、实际 usage 与容器输出；不要用保留任务修环境。
如果暂时无法使用真实模型，报告明确写离线流程验证，最终能力评测仍未完成。
验收：每个计划运行槽位都有状态，失败不会导致整张表缺行。
基础：预检与正式实验数据为什么要分开？

<a id="w11-d03"></a>

## 第 3 天：运行基线

在各任务干净工作区运行基线，按 3 个 repeat_id 留记录。可与改进版交替执行以减小时间差异。
达到次数、时间或费用上限立即停止，写 `budget_exhausted`；不因结果不好额外重试到通过。
保留所有补丁和评分结果。服务商返回缺失用量时记未知并对账。
验收：原始记录包含计划槽位与实际运行差别，模型声明完成与外部通过分别有字段。
基础：独立重复和挑选最好一次的区别。

<a id="w11-d04"></a>

## 第 4 天：运行改进版

使用同样任务、模型和预算条件运行改进版，不因某类任务失败临时更换模型或扩大步骤。
如果遇到实现缺陷需要修复，冻结新版本，明确旧实验哪些作废并重新安排；不混合版本成一个结果。
验收：每行标明真正执行的提交，保留集没有被用作新一轮开发集。
基础：配对比较与不可控随机性。

<a id="w11-d05"></a>

## 第 5 天：统计和限制

每版最多 30 个保留集运行槽位，报告外部通过数 / 计划数，以及完成数、未开始数、预算中断数和环境错误数。
补充已完成样本通过率时明确分母；不能悄悄删掉预算停止后只报告较漂亮比例。
耗时、tokens、费用报告总量和分布，并注明缺失项。逐任务列出三次结果，避免把总均值当成稳定性证明。
验收：另一个人从原始行能复算主表，至少 5 个失败案例可定位。
基础：样本小，不能声称普遍显著或达到大厂招聘门槛。

<a id="w11-d06"></a>

## 第 6 天：复现文档

从新目录按 README 还原依赖、配置、镜像和一个开发样例；密钥通过宿主环境提供，不写进文档。
写清需要联网的安装与模型请求，离线 mock 的替代步骤，以及哪些正式实验没有运行。
把架构、限制和报告链接放进主入口，检查不存在的命令和文件。
验收：别人照着文档能运行一个小例子并找到结果，真实未完成部分清楚列出。
基础：版本锁定与完全复现之间的差距。

<a id="w11-d07"></a>

## 第 7 天：周验收

提交冻结清单、结果主表、原始行、账本、失败分析、复现说明。
通过条件：计分来自外部测试，重复与预算如实记录，任何改善都有对照证据。
聊天入口：“第 11 周，我计划……实际完成……预算中断……这张表的分母是……”。
