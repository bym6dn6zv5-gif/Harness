# 第 5 周：把一次运行变成可以恢复的任务

[回学习时间表](../../docs/study-calendar.md#w05) · [上一周](week04.md) · [下一周](week06.md)

本周主教材任务：会话保存点、写入队列与确认。按 [源码任务表](../source_mastery/curriculum-map.md) 对照 claw-code 与 Codex，
先读 [主讲义](../source_mastery/README.md)，再提交本周 Python 实现与一个失败反例。

周成果：任务中断后从检查点继续，输入冲突时停止，明确说明哪些操作可能重做。
先完成第 9 天只读实验，再扩展到第 4 周的项目。不要把数据库提交等同于文件操作的事务。

<a id="w05-d01"></a>

## 第 1 天：定义恢复需要的状态

概念：内存里的列表在进程退出后消失，磁盘记录才是新进程能读到的事实。
列出 task_id、消息、工作区、工具策略、模型配置、已用预算、输入及修改指纹、状态版本。
小例子：读取后暂停时，消息应是 user → assistant 请求 → tool 结果，不是只有一句“已读取”。
自己设计状态模型，拒绝未知版本与计数不一致；API 密钥不进入状态。
验收：解释删掉其中一个字段会造成什么恢复错误。基础：序列化与对象引用。

<a id="w05-d02"></a>

## 第 2 天：SQLite 保存与读取

把状态 JSON 和 revision 存入一张表；用参数占位符，提交后关闭连接，再重新打开验证。
可先参考 `lesson09.py`，但自己实现一个最小 save/load 往返。
更新时要求旧 revision 一致，防止较旧进程覆盖较新状态；说明这还不能防止重复执行工具。
验收：中文与换行往返不变；坏路径恢复不会新建一个空库；已有任务不被意外覆盖。
基础：事务的提交、回滚和数据库连接的生命周期。

<a id="w05-d03"></a>

## 第 3 天：选择保存边界

画出“发模型请求 → 收回复 → 执行工具 → 保存结果”四个位置，逐个想象中断。
只读工具可以重做；写文件工具要有操作 id、前后指纹和完成记录，恢复前先核对实际文件。
例如预期 A→B：文件仍为 A 可以尝试，已经是 B 应记录已完成，其他内容则冲突停止。
这只是限定替换操作的恢复方案，不宣称任意副作用恰好执行一次。
验收：给每个中断点写出预期动作。基础：幂等与“请求发送但确认丢失”。

<a id="w05-d04"></a>

## 第 4 天：实现 resume

目标入口读取明确 task_id 或数据库路径，恢复原预算、配置与完整历史，再检查工作区。
先用固定模型执行一回合正常退出，然后由另一进程恢复；不要先用随机强制结束掩盖基本流程。
小例子：总预算 3，已用 1，恢复后最多再请求 2 次；再次恢复已完成任务不能增加计数。
验收：两段运行的结果与不中断版本一致，调用 id 无悬空关联。基础：进程参数与持久化标识。

<a id="w05-d05"></a>

## 第 5 天：工作区冲突

为任务真正依赖的文件建清单与指纹，区分用户原始输入和 Harness 已确认的修改。
在自己的临时任务副本中改一个输入，再恢复，要求在新工具调用前报告冲突文件。
不要自动用旧快照覆盖用户改动；明确指纹检查与执行之间仍有竞态，后续可用快照或锁改进。
验收：内容改变、删除、路径替换各有记录；未变化输入可以继续。
基础：哈希证明当前内容相同，不能证明历史上从未变化。

<a id="w05-d06"></a>

## 第 6 天：注入中断，整理恢复矩阵

给存储层注入一次保存失败，给模型层注入请求超时，给补丁层注入“写后、确认前”中断。
每次从新副本开始，比较磁盘、数据库和事件记录三者；记录重做、跳过或停止的依据。
严格付费预算需要在请求前预留额度，并处理结果未知的请求；不能只靠回合末保存的计数。
验收：至少 4 个中断场景有可复现步骤，恢复不会静默重置预算。
基础：状态机与外部系统之间为什么难以原子提交？

<a id="w05-d07"></a>

## 第 7 天：周验收

展示一次跨进程恢复、一次输入冲突、一次写入确认不明的停止。
通过条件：能解释保存边界、重放范围、预算局限和冲突处置；没有用自动覆盖掩盖问题。
聊天入口：“第 5 周，我在……之后中断，磁盘是……检查点是……我准备……”。
