# 第 3 周：手写一个会继续、也会停止的 Agent 循环

本周主教材任务：循环、停止与待处理输入。按 [源码任务表](../source_mastery/curriculum-map.md) 对照 claw-code 与 Codex，
先读 [主讲义](../source_mastery/README.md)，再提交本周 Python 实现与一个失败反例。

周成果：输入问题后，模型通过只读工具定位代码，并用明确状态停止。目标接口与状态见
[工程契约](engineering-contracts.md)。先用固定响应回放，不依赖模型随机表现。

## 第 1 天：先画状态机

用四个状态描述流程：等待模型、执行工具、回传结果、结束。标出坏响应和预算用尽的出口。
小例子是“搜索函数 → 读取文件 → 给出定位说明”，共 3 次模型调用、2 次工具调用。
写一条没有工具结果就再次请求模型的错误历史，说明错在哪里。
验收：同学只看图就知道每个分支何时继续。基础：for 与 while 的停止条件。

## 第 2 天：独立重写循环

先关掉 `lesson03.py`，根据状态图写自己的版本。每次接收回复后检查类型和角色；
如果是工具请求，分发并追加带 id 的结果；如果是非空最终文本，记录 `model_finished`。
一个 step 约定为一次模型请求，最终回答也计数。
验收：固定三段响应得到 3/2 的计数和完整消息顺序。
提示：先支持单次工具调用，不同时加入并行工具。基础：可变列表的引用。

## 第 3 天：工具失败也要回传

设计 mock 请求不存在文件，工具返回 `file_not_found` 后模型改为搜索或解释失败。
不同错误保留稳定的 code 和可读 message；不要把错误静默变成空文本。
模型声明结束只设置运行状态，任务是否修好还要由第 8 周外部评分判断。
验收：坏参数、文件缺失、未知工具均能闭合消息关系，循环不崩溃。
基础：预期错误与程序缺陷如何区分？

## 第 4 天：步数和调用预算

用不断重复读取的 mock 验证上限。上限 2 时只能产生两次模型回复，不能再多请求一次才检查。
同时设计工具尝试次数与实际执行次数，避免权限拒绝也被记录为已执行。
时间与金额预算先留字段，不使用假估算冒充真实账单。
验收：0、负数、bool 的上限被拒绝；1 和 2 的边界准确。基础：循环不变量。

## 第 5 天：重复与协议错误

区分重复调用 id 与相同动作：id 重复可能破坏协议，相同动作有时是合理重读。
先拒绝重复 id，再记录相同 name+规范化参数的连续次数；达到你明确写下的阈值后停止或反馈。
给“文件已变化后的合理重读”留后续改进问题，别粗暴禁止所有重复。
验收：坏 JSON、空回答、缺参数、重复 id 均有停止原因，未额外执行工具。
基础：集合查重与列表查重的复杂度。

## 第 6 天：命令入口与问题定位

实现未来 `run` 的参数：工作区、问题、模型模式、最大步数；先只支持 mock。
在两个自建文件中埋一个简单分支问题，让回放响应搜索、读取并指出位置，不修改文件。
结果包含状态、原因、消息和调用数； CLI 退出码与内部任务状态分别写文档。
验收：从项目目录外指定绝对工作区仍可定位；缺失工作区清楚报错。
基础：argparse 与进程参数列表。

## 第 7 天：周验收

不看参考写一个最小循环，讲清工具错误如何回来、预算在哪检查、谁判断任务成功。
通过条件：可定位问题、无无限循环、协议错误可解释。运行日志附在周复盘中。
聊天入口：“第 3 周，我的停止状态是……对应消息最后三条是……”。
